# KeyHelp API coverage

The app talks to the **KeyHelp REST API v2**, documented version **2.15** (OpenAPI document
"KeyHelp RESTful API", the version a current KeyHelp install ships in `/api/openapi.json`; public
copy at [api.keyhelp.de](https://api.keyhelp.de) and on
[SwaggerHub](https://app.swaggerhub.com/apis-docs/keyhelp/api/2.15)). Only endpoints that the
document lists are used.

- Base URL: `https://<panel>/api/v2/<endpoint>`; https only.
- Authentication: the `X-API-Key` header. Keys are created in KeyHelp under
  *Configuration → API* and should be limited to the IP addresses you connect from. The API is
  off by default and has to be turned on there.
- Answers are JSON (`Accept: application/json`). Errors have the body `{"code", "message"}`.
- A GET that hits the web server reload after a change (500/503, see the API's own hints) is
  retried once after three seconds. Writes are never retried.

## Endpoints the app uses

| Endpoint | Method | Where in the app |
|---|---|---|
| `/ping` | GET | Connect: checks address and key before anything is saved |
| `/server` | GET | Status: host, OS, panel version, uptime, load, disk, memory, swap, inodes, mail queue, updates, components, service ports; alerts |
| `/clients` | GET, POST | Clients list and search; new client (password generated by the server when left empty) |
| `/clients/{id}` | GET, PUT | Client detail; edit (e-mail, notes, contact); disable/enable (`is_suspended`) |
| `/clients/{id}/stats` | GET | Client detail: disk and resource usage against the limits |
| `/hosting-plans` | GET | New client: hosting plan choice |
| `/domains` | GET, POST | Domains list with certificate state; new domain (Let's Encrypt, www, e-mail) |
| `/domains/{id}` | GET, PUT | Domain detail; disable/enable (`is_disabled`) |
| `/certificates` | GET | Certificate expiry on domains, the certificates list and alerts |
| `/emails` | GET, POST | E-mail accounts list with quota; new account (password generated when left empty) |
| `/emails/{id}` | GET, PUT | Mailbox detail; password reset (given or server-generated) |
| `/databases` | GET, POST | Databases list; new database (names and password generated when left empty) |
| `/ftp-users` | GET | FTP users list |
| `/scheduled-tasks` | GET | Scheduled tasks (cron) list with error state |
| `/backups/operations` | GET | Backups list; failed-backup alerts (`started_after`) |

Values the server generates (passwords, database names) come back once in the POST/PUT answer;
the app shows them once and does not store them.

## Not used (yet)

| Endpoint | Why not |
|---|---|
| `POST /server/reboot` | Too drastic for a phone tap in a first version |
| `DELETE` on any object | Deleting is left to the panel; the app only disables (clients, domains) |
| `/admins`, `/login/{id}` | Admin accounts and one-click login URLs: possible later |
| `/dns/{id}` | The DNS editor needs a proper record editor |
| `/directory-protections`, `/fail2ban/banned-ips` | Candidates for a later version (unban an IP) |
| `/clients/{id}/traffic`, `/clients/{id}/resources` | The detail screen builds the same view from the lists |

## What the API does not offer

- No push or webhook: alerts come from the app's own periodic check (see
  [alerts.md](alerts.md)).
- No service status beyond the `ports` list of `/server` (service name, port, online/offline).
- No log access, no backup start: backup operations can only be read.

## Mock server

`src/mock/server.ts` implements the endpoints above in memory, with the documented status codes,
error bodies and generated values, and checks the key. The unit tests use it through `fetch`, the
e2e run answers the web app's requests with it (Playwright `page.route`). The data in
`src/mock/fixtures.ts` is invented and uses reserved example names.
